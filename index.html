        DB
        
Backend truth

        
The layer most portfolios skip. A thin, driver-agnostic DBUtility wrapper proves the UI told the truth — and swaps to Postgres by changing one constructor.

        
    
          
  • Parameterized queries only — injection-proof by design
    • 
          
  • fetch_one / fetch_all / execute
    • 
          
  • Seeded from a script, so CI can rebuild it from scratch
    • 
        

      

    


    
    
Why this framework holds up

    

      

        01
        
One BasePage, not 40 try/except blocks

        
Error handling and logging live in exactly one class. Every page object inherits click, fill, assert_url — so a change to how failures are logged is a one-file edit, not a repo-wide find-and-replace.

      

      

        02
        
Environments are a flag, not a code change

        
pytest --env dev|qa|prod. An EnvManager reads .env and resolves the base URL once per session; every test follows automatically with zero test-code changes.

      

      

        03
        
Fixture scope matches blast radius

        
Four conftest.py files — root, ui, api, db. A browser fixture never loads for an API test that has no browser. Expensive things (API contexts, DB connection, resolved URL) are session-scoped; anything needing isolation is per-test.

      

      

        04
        
Parallel-safe on purpose

        
-n auto --dist loadgroup. Dependent test chains are pinned to a single worker with @pytest.mark.xdist_group — a fix that came from a real parallel-only failure, not from theory.

      

      

        05
        
Evidence only when it matters

        
Screenshot, video and full trace are captured retain-on-failure, and a pytest_runtest_makereport hook attaches the failure screenshot straight into Allure — no hunting through folders.

      

      

        06
        
Three ways to run it in CI

        
GitHub Actions workflow, a Dockerfile built on Microsoft's official Playwright image, and a parameterised Jenkinsfile — all three seed their own data and publish their own reports.

pages/ — the Page Object Model

        
One class per screen. Locators are defined in __init__ and resolved lazily by Playwright; every other method performs an action or an assertion. Because everything inherits BasePage, a DOM change touches exactly one file and never leaks into a test.

        
base_page · login_page · home_page · cart_page · checkout_info_page · checkout_overview_page

# every page object inherits this — error handling exists in ONE place
class BasePage:
    def __init__(self, page: Page):
        self.page = page

    def click(self, locator: Locator, description: str = "") -> None:
        try:
            locator.click()
            logger.info(f"Clicked on {description or locator}")
        except Exception as exc:
            logger.error(f"Failed to click {description}: {exc}")
            raise

    def assert_url(self, expected_url: str) -> None:
        # auto-retrying assertion — survives a navigation that hasn't landed yet
        expect(self.page).to_have_url(expected_url)



# override pytest-playwright's own fixtures — merge, don't replace
@pytest.fixture(scope="session")
def base_url(pytestconfig) -> str:
    env = pytestconfig.getoption("--env")
    return EnvManager.get_base_url(env)

@pytest.fixture(scope="function")
def browser_context_args(browser_context_args, base_url):
    # the parameter resolves to the PLUGIN's fixture, so this layers on top
    return {**browser_context_args, "base_url": base_url, "no_viewport": True}

@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed:
        page = item.funcargs.get("page")          # None for API/DB tests
        if page:
            allure.attach(page.screenshot(), name="failure")



# one test function, three real scenarios — positive AND negative
@pytest.mark.sanity
@pytest.mark.parametrize(
    "username, password, expect_success",
    [
        ("standard_user",   "secret_sauce", True),
        ("locked_out_user", "secret_sauce", False),
        ("standard_user",   "wrong_pass",   False),
    ],
)
def test_login_scenarios(self, username, password, expect_success):
    self.login_page.login_to_application(username, password)
    if expect_success:
        self.login_page.verify_dashboard_url()
    else:
        assert self.login_page.get_error_message()

Practices I hold the line on

    

      
◆
Page Object Model
Where things are on screen never leaks into what we're checking.

      
◆
Config-driven, not hard-coded
URLs, credentials, payloads and schemas all live in test_data/.

      
◆
Fixtures over setup code
Scoped deliberately; autouse only where every test genuinely needs it.

      
◆
Data-driven & negative paths
Happy path proves it works. Negative paths prove it fails correctly.

      
◆
Parameterized SQL, always
Never an f-string in a query. Injection-proof by construction.

      
◆
Secrets hygiene
.env gitignored, .env.example committed — the habit that matters.

      
◆
Structured logging
One logger factory, console + rotating file, module name on every line.

      
◆
Markers as suite slices
smoke in CI, regression nightly — same repo, different budgets.

      
◆
Retry once, then believe it
One rerun catches a network blip; a real bug still fails twice.

      
◆
Cross-browser by default
Chromium, Firefox and WebKit in the CI matrix — not a manual afterthought.

      
◆
Documentation as a deliverable
A full architecture guide, not a README with an install command.

      
◆
Extensible on purpose
New page, new endpoint, new environment or a real Postgres — each is a documented recipe.

          Featured · AI + Testing
          
AI Test Failure Analyzer for Playwright

          

            A failed test spits out a screenshot, a video, a trace, console errors, network errors and a
            stack trace — and a human has to open all of it to answer one question: real bug, flaky
            test, or broken locator? This tool collects the whole evidence bundle automatically,
            classifies it for free, and only calls an LLM when a human explicitly asks it to.
          

        


        

          

            
What it does

            
    
              
  • Auto-captures screenshots, video, traces, console/network logs and stack traces on every failure
    • 
              
  • A free, deterministic rule-based classifier triages every failure in seconds — useful on day one, no API key needed
    • 
              
  • An opt-in AI layer (OpenAI / Claude, pluggable provider) returns a structured root-cause report: confidence, severity, suggested fix, improved locator
    • 
              
  • A Streamlit dashboard for execution summaries, failure trends and flaky-test tracking, linked to pytest-html and Allure
    • 
            

          

          

            
The engineering decisions

            
    
              
  • Two call sites, total. An LLM can only be invoked from one function — so “does this ever call an API automatically?” is verifiably answerable: no. CI never spends a cent.
    • 
              
  • Pydantic-validated output. A schema turns “please return valid JSON” from a polite request into an enforced contract; invalid data never reaches the database.
    • 
              
  • Strictly layered. Nothing in a lower layer imports from a higher one — database/ never imports dashboard/.
    • 
              
  • ast-based source extraction. Only the failing test function is sent to the model, not the whole file.
    • 
              
  • Constructor-injected repository. Every DB test runs against a real in-memory SQLite engine with zero mocking.
    •
